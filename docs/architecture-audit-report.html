一、安全 (Security) — 9 个问题

后端 CORS 全放行、OAuth state 无签名、session token 暴露在 URL 中、加密密钥派生方式薄弱。

P0 安全 CORS 配置为通配符 `*`，允许任意来源携带凭证访问 API worker/src/index.js:103

Access-Control-Allow-Origin: '*' 允许任何网站发起跨域请求。虽然 API 需要 Authorization Bearer token 认证，但恶意网站可以通过钓鱼页面诱导用户访问，利用浏览器中已存储的 session token 发起跨域请求。

更危险的是：如果用户在浏览器中打开了恶意页面，该页面可以通过 fetch 携带用户的 token（如果存在 localStorage 或 cookie 中）向 Worker API 发起请求，读取或删除用户数据。

修复建议
将 CORS origin 限制为 chrome-extension://<extension_id> 和 https://trae-token-watcher-api.ai-kits.workers.dev。从请求头 Origin 中读取来源，与白名单比对后动态返回。
P0 安全 OAuth state 参数仅 base64 编码，无密码学签名，CSRF 防护形同虚设 worker/src/auth.js:17-24

state = btoa(JSON.stringify({extId, nonce})) — nonce 虽然是随机 UUID，但从未存储在服务端，回调时也未验证 nonce。攻击者只需 base64 编码一个 JSON 对象即可伪造合法的 state 参数。

这意味着攻击者可以构造一个伪造的 GitHub OAuth 回调 URL，诱导用户访问，将攻击者的 GitHub 账号绑定到用户的扩展 session 上（账户劫持）。

修复建议
1. 在 KV 中存储 state → {extId, createdAt}，TTL 5 分钟；
2. 回调时验证 state 存在且未过期，用后即焚；
3. 或用 HMAC-SHA256 对 state 签名（密钥用 SESSION_SECRET），回调时验签。
P1 安全 Session token 通过 URL query 参数传递，存在泄露风险 worker/src/auth.js:89-96

OAuth 完成后，Worker 302 重定向到 /auth/done?token=xxx&expires=xxx。token 出现在 URL query 中，可能被以下途径泄露：

1. Cloudflare Workers 的访问日志（如果开启了 observability）
2. 浏览器历史记录
3. Referer 头（如果 /auth/done 页面加载了外部资源）

代码注释说"chrome.tabs API 看不到 fragment"，这是正确的，但可以用 chrome.webNavigation API 或在 /auth/done 页面中注入 content script 来读取 fragment。

修复建议
方案 A：将 token 放在 fragment (#token=xxx) 中，在 /auth/done 页面注入一段 JS 读取 fragment 并通过 chrome.runtime.sendMessage 发给扩展。
方案 B：用短期一次性 code（5 秒过期）替代 token，扩展用 code 换 token（类似 PKCE 流程）。
P1 安全 AES 密钥派生方式薄弱，直接用 SHA-256(secret) 作为 AES key worker/src/github.js:101-103

deriveAesKey() 直接对 SESSION_SECRET 做 SHA-256 得到 AES-256 key。这是非标准的密钥派生方式，缺乏：

1. 盐值（salt）— 相同 secret 永远派生出相同 key
2. 迭代次数 — 无计算成本，暴力破解容易
3. 密钥分离 — session 签名和 token 加密用同一个 secret，一旦泄露两道防线同时崩溃

修复建议
使用 HKDF 或 PBKDF2：crypto.subtle.deriveKey({name:'HKDF', hash:'SHA-256', salt, info:'github-token-enc'}, ...)。为不同用途（session 签名 vs token 加密）使用不同的 info 参数实现密钥分离。
P1 安全 postMessage 使用通配符 `*` 作为 targetOrigin extension/content/inject.js:104

window.postMessage({...}, '*') 允许页面上任何脚本（包括第三方注入的）接收消息。虽然 payload 不含敏感信息（token 用量数据），但在某些场景下可能泄露用户的使用习惯。

同样，content.js 中 window.postMessage({...}, '*') 也是通配符。

修复建议
inject.js 中改为 window.postMessage({...}, location.origin)；content.js 中同理。或定义自定义 targetOrigin 常量。
P1 安全 sync push 接口无速率限制，可被滥用进行数据注入 worker/src/sync.js:12-70

/api/sync/push 接受 500 条/请求，无任何速率限制。一个有效的 session token 可以在短时间内推送大量垃圾数据到 D1 数据库，导致：

1. D1 存储配额耗尽（免费版 5GB）
2. 正常用户的 pull 操作被垃圾数据淹没
3. D1 写入配额耗尽（免费版每天有限额）

修复建议
1. 用 KV 实现简单的速率限制：每用户每小时最多 N 条记录
2. 或用 D1 的 usage_quota 表扩展为 sync 配额
3. 对单条记录做更严格的字段验证（ts 范围、token 数量上限等）
P2 安全 DeepSeek API Key 明文存储在 chrome.storage.local extension/popup/popup.js:505

用户的 DeepSeek API Key 以明文存储在 chrome.storage.local。虽然扩展的 storage 有一定隔离性，但任何能访问浏览器 profile 目录的程序或扩展都可以读取。

修复建议
至少做一层简单的混淆（XOR + base64），或使用 chrome.storage.session（内存级，浏览器关闭即丢失）。更好的方案是提醒用户用完即删。
P2 安全 sync push 的 flo() 函数允许负数积分/费用写入 worker/src/sync.js:207

function flo(v) { const n = Number(v); return Number.isFinite(n) ? n : 0; } — 不检查负数。攻击者可以推送 credits: -99999 的记录，虽然目前没有直接影响（数据仅用于展示），但可能误导统计或用于未来功能。

修复建议
改为 return Number.isFinite(n) ? Math.max(0, n) : 0;
P2 安全 诊断接口错误信息暴露 DeepSeek API 原始响应 worker/src/diagnose.js:96

throw httpError(502, 'DeepSeek API 错误 ${resp.status}: ${errText.slice(0, 200)}') — 将 DeepSeek 的原始错误响应（可能包含 API key 片段、内部错误信息）返回给客户端。

修复建议
客户端只返回通用错误信息（"诊断服务暂时不可用"），原始错误仅记录在服务端日志中。

二、性能 (Performance) — 9 个问题

IndexedDB 连接管理、全量数据加载、定时器频率、响应体克隆是主要性能瓶颈。

P0 性能 IndexedDB 每次操作都重新打开和关闭连接，严重浪费性能 extension/lib/db.js:9-58

每个 addRecord()、getRecordsSince()、getAllRecords() 等函数都调用 openDB() 创建新连接，并在 tx.oncomplete 中关闭。这意味着：

1. 每次操作都有 IDB 打开/关闭开销（约 5-20ms）
2. 多个并发操作会各自打开连接，可能触发 onupgradeneeded 冲突
3. 在 background.js 中，每次写入用量记录 + refreshBadge + checkAlert 会触发至少 3 次 DB 开关

修复建议
使用单例模式：let dbPromise = null; function getDB() { if (!dbPromise) dbPromise = openDB(); return dbPromise; }。所有函数复用同一个 Promise。注意处理 onversionchange 事件。
P1 性能 getSummary() 加载全部 2000 条记录到内存并多次遍历 extension/lib/db.js:161-273

getAllRecords(2000) 一次性加载 2000 条记录，然后对同一数组进行 4 次遍历：

1. buckets 汇总（today/week/month/all）
2. trend 按天聚合
3. byModel 按模型聚合
4. bySession 按会话聚合

对于使用频繁的用户，2000 条记录每条含 url、userInputPreview 等长字符串字段，可能占用数 MB 内存。这个函数每 5 秒被调用一次（popup 打开期间）。

修复建议
1. 单次遍历完成所有聚合（reduce 模式）
2. 在 IndexedDB 层面用 cursor + 索引做范围查询，避免全量加载
3. 缓存 summary 结果，仅在新记录到达时失效
4. popup 的 5 秒刷新改为事件驱动（storage change 监听）
P1 性能 refreshBadge() 每次写入都全量查询今日所有记录 extension/background/background.js:161-178

每写入一条用量记录就调用 refreshBadge()，内部调用 getRecordsSince(startOfDay(Date.now())) 加载今日全部记录，仅为获取 count。如果今天有 200 次请求，第 200 次写入时仍会加载全部 200 条记录。

修复建议
1. 用 IndexedDB store.count() 替代 getAll()，只获取数量不加载完整记录
2. 或维护内存计数器，写入时 +1，无需查询
P1 性能 fetch 拦截器对每个匹配响应都 clone 并读取完整文本 extension/content/inject.js:677-684

对每个匹配 shouldIntercept() 的 fetch 响应，代码调用 response.clone().text() 读取完整响应体。对于大型 JSON 响应（如会话列表、代码补全结果），这可能达到数 MB，导致：

1. 内存翻倍（clone + text）
2. JSON.parse 在主线程执行，阻塞页面
3. SSE 响应可能持续增长，text() 等待完成

修复建议
1. 对 SSE/EventSource 响应用 ReadableStream 逐块解析，不等完整 body
2. 对 JSON 响应先检查 Content-Length，超阈值（如 100KB）跳过
3. 用 response.json() 替代 text() + JSON.parse，减少一次拷贝
P1 性能 popup.js 每 5 秒全量刷新，包含 6+ 次 IndexedDB 查询 extension/popup/popup.js:1033

setInterval(renderSummary, 5000) 触发：

1. getSummary() → getAllRecords(2000)
2. getAllRecords(20)（最近记录）
3. predictUsage() → getRecordsSince(now - 14*dayMs)
4. getComparison() → getRecordsSince(now - 61*dayMs)
5. checkAlert() → 再次调用 predictUsage()（重复查询！）
6. getDiagnoses(50)

一次刷新至少 6-7 次 IDB 查询，且 predictUsage 被 checkAlert 重复调用。

修复建议
1. 改为事件驱动：监听 background 的写入通知，仅在有新数据时刷新
2. 合并 IDB 查询：一次 getAllRecords 满足所有计算
3. 缓存 predictUsage 结果，checkAlert 复用而非重新查询
4. Tab 切换时才渲染当前 tab 的数据，不渲染隐藏 tab
P1 性能 getComparison() 加载 61 天全部记录用于 3 个时间范围对比 extension/lib/db.js:492-536

加载 61 天的记录（可能数千条），仅为计算今日 vs 昨日、本周 vs 上周、本月 vs 上月的对比。完全可以分范围查询。

修复建议
用 3 个独立的 IDBKeyRange 查询分别获取各范围记录，或用 cursor 边遍历边累加。
P2 性能 内存中的 Map 清理策略依赖 size 阈值，非定时清理 extension/content/inject.js:109, 592

ctxCache（60s TTL）只在 size > 50 时清理过期项。seenRequests（3s 窗口）只在 size > 200 时清理。如果 Map 增长缓慢（如每秒 1 条），过期项不会被及时清理，直到达到阈值。

修复建议
用 setInterval 定时清理（每 30 秒一次），或用 WeakRef + FinalizationRegistry。
P2 性能 content.js 浮窗拖拽时全局 mousemove 监听器未解绑 extension/content/content.js:310-326

document.addEventListener('mousemove', ...) 在浮窗创建时注册，但 removeWidget() 时未移除。虽然回调内有 if (!dragging) return，但每帧仍会触发事件分发和回调执行，影响页面滚动和动画性能。

修复建议
在 mouseup 后移除 mousemove 监听器（只在拖拽时注册），或在 removeWidget 时移除所有监听器。
P2 性能 debug 日志在非调试模式下仍会计算 bodyPreview extension/content/inject.js:680

pushDebug({bodyPreview: text.slice(0, 2000)}) — text.slice(0, 2000) 总是执行，即使 DEBUG 为 false（pushDebug 内部 return）。对于大响应体，slice 操作仍有开销。

修复建议
在调用 pushDebug 前先检查 if (DEBUG)，或用惰性求值。

三、稳定性 (Stability) — 8 个问题

MV3 Service Worker 生命周期管理是最突出的稳定性风险，其次是代码级别的猴补丁和竞态条件。

P1 稳定性 Service Worker 生命周期导致 OAuth 回调状态丢失 extension/background/background.js:74

awaitingOAuthCallback = true 是内存变量。MV3 的 Service Worker 在 30 秒不活跃后会被终止。如果用户在点击"GitHub 登录"后，在 GitHub 授权页停留超过 30 秒（很常见），SW 被终止，awaitingOAuthCallback 重置为 false，回调永远不会被捕获。

结果：用户完成了 GitHub 授权，但扩展永远收不到 token，登录卡死。

修复建议
不用内存变量做状态标记。改为在 chrome.storage.session 中设置 ttw_oauth_pending: true（session 级别存储，SW 重启后仍可读取）。chrome.tabs.onUpdated 监听器在 SW 重启后会自动重新注册（声明式事件），回调时从 storage 读取状态。
P1 稳定性 handleUsage 被猴补丁（monkey-patch）覆盖，代码可维护性差 extension/background/background.js:262-266

文件底部：

const _origHandleUsage = handleUsage;
handleUsage = async function(payload, sender) {
await _origHandleUsage(payload, sender);
runAlertCheck();
};

这种模式的问题：

1. 消息监听器在第 17 行绑定了原始 handleUsage，但 JS 中函数声明会 hoisting，而赋值在文件末尾执行 — 监听器绑定的可能是原始函数而非补丁后的
2. 实际上由于 switch 中直接调用 handleUsage(msg.payload, sender)，在 JS 中这会在调用时解析为最新的绑定，所以可能 work — 但这是脆弱的
3. 如果未来有人在 handleUsage 和补丁之间添加 return，补丁会被跳过

修复建议
直接在 handleUsage 函数体内调用 runAlertCheck()，删除文件底部的猴补丁代码。
P1 稳定性 syncTimer 在 Service Worker 被终止后丢失，debounce 同步失效 extension/background/background.js:105-113

syncTimer = setTimeout(...) 是内存变量。SW 被终止后，timer 被清除，debounced sync 不会执行。虽然 chrome.alarms.create(SYNC_ALARM, {periodInMinutes: 10}) 提供了兜底，但 30 秒 debounce 的实时性丢失。

修复建议
用 chrome.alarms.create('ttw-sync-debounce', { delayInMinutes: 0.5 }) 替代 setTimeout。SW 重启后 alarm 仍有效。
P2 稳定性 WebSocket 构造函数未正确转发 protocols 参数 extension/content/inject.js:808-838

window.WebSocket = function(...args) { const ws = new OriginalWebSocket(...args); ... } — 虽然用 spread 转发了所有参数，但 WebSocket.prototype 的赋值方式不完整：window.WebSocket.prototype = OriginalWebSocket.prototype 意味着 instanceof 可能不可靠（不同构造函数共享同一 prototype）。

更关键的是：如果页面代码检查 ws.constructor === WebSocket，会得到 false（因为构造函数已被替换）。

修复建议
用 Proxy 包装而非直接替换：window.WebSocket = new Proxy(OriginalWebSocket, { construct(target, args) { ... } })。
P2 稳定性 EventSource onmessage 属性拦截可能导致内存泄漏 extension/content/inject.js:789-795

Object.defineProperty(es, 'onmessage', {...}) 重写了 onmessage setter，但新 setter 只存储了回调引用，没有实际注册到 EventSource 上。这意味着如果页面通过 es.onmessage = fn 设置监听器，fn 不会被 EventSource 调用 — 页面收不到消息！

修复建议
在 setter 中同时注册到 EventSource：set: (fn) => { _onmsg = fn; origAdd('message', fn); }。注意避免重复注册。
P2 稳定性 IndexedDB 迁移时 cursor 更新无错误处理 extension/lib/db.js:32-43

v1→v2 迁移用 cursor 遍历旧记录回填 clientId，cursorReq.onsuccess 中 cursor.update(rec) 没有 onerror 处理。如果某条记录更新失败（如 quota 超限），cursor 会停止但不会报错，导致部分记录有 clientId、部分没有。

修复建议
为 cursor.update(rec) 添加 onsuccess 和 onerror 处理，记录失败数量并在迁移完成后输出警告。
P2 稳定性 importRecords 中的 pending 计数器存在竞态条件 extension/lib/db.js:678-734

多个 checkReq.onsuccess 回调中递减 pending，然后在 pending === 0 时设置 tx.oncomplete。但如果所有 checkReq 在同一个事件循环中完成，tx.oncomplete 可能在事务已经完成后才设置，导致 resolve 永远不触发。

修复建议
在循环开始前就设置 tx.oncomplete，用外部变量跟踪 imported/skipped 计数。
P2 稳定性 content.js 浮窗 refreshTimer 在 SPA 路由切换后可能残留 extension/content/content.js:128-129

refreshTimer = setInterval(refreshWidgetData, 15000) 在 createWidget 时创建，removeWidget 时清除。但 work.trae.cn 是 SPA，如果页面做客户端路由切换（不刷新页面），content script 不会重新注入，旧的 widget 和 timer 会继续运行。如果页面在路由切换时清除了 DOM，widget host 可能变成孤儿节点。

修复建议
监听 document.body 的 MutationObserver，检测 widget host 是否被移除，如果是则清理 timer 和状态。

四、可靠性 (Reliability) — 10 个问题

数据验证缺失、无超时/重试机制、外部依赖故障无降级是核心可靠性风险。

P1 可靠性 DeepSeek API 调用无超时和重试机制 worker/src/diagnose.js:77-101, extension/popup/popup.js:597-621

Worker 端和扩展端的 DeepSeek API 调用都使用裸 fetch，无超时、无重试。如果 DeepSeek API 响应慢（>30 秒）或间歇性失败：

1. Worker 端：Cloudflare Workers 有 CPU 时间限制（免费版 10ms，付费版 30s），但 fetch 等待不算 CPU 时间 — 请求会挂起直到客户端超时
2. 扩展端：popup 中用户会看到"正在分析..."永远转圈
3. 配额已扣但结果未返回（Worker 端 incrementQuota 在 callDeepSeek 之后）

修复建议
1. 用 AbortController 设置 30 秒超时
2. 对 5xx 错误做 1 次重试（间隔 1 秒）
3. 将 incrementQuota 移到 callDeepSeek 成功后（已如此，确认无误）
4. 超时后给用户明确的错误提示和重试按钮
P1 可靠性 Snowflake ID 时间反推是未文档化的启发式假设 extension/content/inject.js:438-446

代码假设 TRAE 的 session_id 前 8 位十六进制 = 创建时间的秒数。虽然注释说"已用真实样本验证"，但这不是官方 API 契约。如果 TRAE 更改 ID 生成策略（如改用 UUID、增加机器位、更改时间戳精度），这个假设会静默失效，导致：

1. 历史会话被归到错误的时间（2020 年或 2033 年）
2. 今日用量统计错误
3. 趋势图数据混乱

且 deriveTimeFromSessionId 的合理区间检查（1577836800 ~ 2000000000）会在 ID 非法时返回 null，但如果新策略的 ID 恰好落在这个区间，错误数据会被静默接受。

修复建议
1. 添加运行时检测：如果连续 N 条记录的 snowflake 时间与 chat_sessions.created_at 偏差超过 10 秒，输出告警并禁用 snowflake 反推
2. 在文档中明确标注这是非官方假设
3. 考虑在 snowflake 反推前先检查 chat_sessions 映射（已有，但映射命中率取决于用户行为）
P2 可靠性 客户端 addRecord 无数据校验，可写入非法值 extension/lib/db.js:72-120

addRecord 接受任意字段，不做校验：

1. 负数 token（inject.js 的 validateUsage 检查了 >= 0，但 background.js 的 spread 操作 payload.inputTokens || 0 不检查负数）
2. 超大 timestamp（如未来 100 年）
3. 超长字符串字段（url、model 可无限长）
4. 非数字类型（如果 inject.js 解析出 NaN，|| 0 会变成 0）

修复建议
在 addRecord 入口做白名单字段过滤 + 类型/范围校验。Math.max(0, Math.floor(n)) 对 token 数，String(v).slice(0, 2000) 对字符串。
P2 可靠性 官方 Worker 不可达时无降级策略 extension/lib/auth.js:99-122

refreshAuthStatus() 在 fetch 失败时返回 {offline: true}，但登录流程 (loginWithGitHub) 不会检测 Worker 是否可达 — 直接打开 Worker URL。如果 Worker 挂了，用户会看到 GitHub 授权页 404 或跳转失败，没有明确的错误提示。

修复建议
在打开 OAuth URL 前先 fetch /health 检查 Worker 可达性。不可达时提示用户"后端服务暂时不可用，请稍后重试或使用自有 Key 模式"。
P2 可靠性 云同步无冲突检测和解决机制 worker/src/sync.js:27-56

两台设备同时修改同一会话的用量记录（由于覆盖式去重，同一 session_id 只保留一条），push 时 INSERT OR IGNORE 会静默丢弃后到的记录。这意味着：设备 A 的记录覆盖了设备 B 的，但设备 B 的 push 被忽略。pull 时两台设备看到的是先 push 的那台的记录，而非最新的。

修复建议
1. push 时用 INSERT OR REPLACE，比较 ts 字段决定是否覆盖
2. 或增加 updated_at 字段，只在记录更新时才覆盖
3. 在 pull 结果中标记冲突记录，让客户端选择保留哪条
P2 可靠性 导出功能无数据完整性校验 extension/options/options.js:306-326

CSV/JSON 导出不包含校验和或记录数验证。如果导出过程中 IndexedDB 数据被修改（新记录写入），可能导致导出的记录数与预览不一致。JSON 导出虽然包含 summary，但没有 checksum 验证。

修复建议
1. 导出时锁定读取范围（记录 startTs/endTs），在文件中包含记录数和 checksum
2. 导入时验证 checksum
P2 可靠性 sync pull 的游标汇报是 fire-and-forget，可能丢失 extension/lib/sync.js:138-145

fetch('/api/sync/cursor', {...}).catch(() => {}) — 如果游标汇报失败（网络错误），本地游标已更新但服务端未更新。下次 pull 会从旧游标开始，重复拉取已导入的记录。虽然有 clientId 去重保护，但浪费带宽和 CPU。

修复建议
将游标汇报改为 await，失败时不更新本地游标。或在 pull 时用 since 参数从服务端获取上次确认的游标。
P2 可靠性 getAllRecords 无分页保护，大数据量可能 OOM extension/lib/db.js:138-158

cursor 遍历到 limit 条后停止，但每条记录的 url 和 userInputPreview 可能很长（各 2000 字符）。2000 条记录 × 4KB/条 ≈ 8MB。在 popup（内存受限环境）中可能触发浏览器内存限制。

修复建议
1. 在查询时只选取需要的字段（IndexedDB 不支持投影，但可以在遍历时裁剪）
2. 降低默认 limit 到 500
3. 对 url/userInputPreview 做长度限制（写入时截断）
P2 可靠性 Worker 错误处理不区分客户端错误和服务端错误 worker/src/index.js:76-81

catch (err) { const status = err.status || 500; ... if (status >= 500) console.error(...) } — 所有错误都返回 {error: message}，客户端无法区分"网络错误"和"业务错误"。4xx 错误也被包装成 JSON 返回，但缺少错误码（error code）供客户端程序化处理。

修复建议
统一错误响应格式：{error: message, code: "NOT_STARRED" | "QUOTA_EXCEEDED" | ...}。
P2 可靠性 OAuth 登出只删除服务端 session，未清理扩展端存储的 session extension/lib/auth.js:69-80

logout() 先 fetch 通知后端删除 session（fire-and-forget），然后 clearSession() 清除本地。如果 fetch 失败（网络错误），后端 session 仍然有效 — 虽然本地已清除，但后端存在的 session token 如果被截获仍可使用。

修复建议
logout 时 await fetch，失败时提示用户"本地已登出，但服务端 session 可能未清除，将在过期后自动失效"。session TTL 7 天是合理的兜底。

五、代码质量 (Code Quality) — 5 个建议

不影响功能但影响长期可维护性的改进建议。

P2 质量 工具函数在 popup.js / content.js / options.js 中重复定义

fmt()、escapeHtml()、shortModel() 在三个文件中各自定义了一遍。startOfDay() 在 db.js 和 background.js 中各有一份。应提取到 lib/utils.js 中统一导出。

P2 质量 整个项目无 TypeScript，复杂的数据结构缺乏类型保护

用量记录有 15+ 个可选字段，session 有 5 个字段，同步状态有 3 个字段。这些数据在 background → db → popup → worker 之间流转，任何一个环节拼错字段名都不会报错，只会静默 undefined。TypeScript 的 JSDoc 模式（// @ts-check）可以在不改变现有构建流程的情况下提供类型检查。

P2 质量 无任何单元测试或集成测试

核心逻辑如 extractUsage、parseSSE、deriveTimeFromSessionId、getSummary 的正确性完全依赖手动测试。这些函数处理的是外部 API 响应，格式可能随时变化，没有回归测试保护非常危险。

P2 质量 magic number 散布在代码中，无集中配置

DEDUP_WINDOW = 3000、SESSION_MAP_MAX = 400、CTX_TTL = 60000、SAMPLE_LIMIT = 2、debugLog.length > 300、SYNC_DEBOUNCE_MS = 30000 等。应集中到一个 config 模块中。

P2 质量 manifest.json 版本号为 0.1.0 但 README 描述了 v8 迭代，版本管理脱节

inject.js 注释标注为 v8，但 manifest.json 的 version 仍为 0.1.0。应建立语义化版本号与代码迭代版本的对应关系，便于用户和开发者追踪变更。
