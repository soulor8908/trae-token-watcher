✓ 本轮（2026-08-13）新修复的问题

  • P1-1 性能：getSummary() 不再 getAllRecords(2000) 全量加载，改为 getRecordsSince(近30天) 的 timestamp 索引范围查询；popup 改为监听 background 发布的 ttw_usage_ping 事件驱动刷新 + 15s 兜底轮询，并加渲染并发守卫（extension/lib/db.js · popup.js · background.js）
  • P1-2 性能：fetch 拦截器新增 4MB 体积护盾，content-length 超限则跳过 clone().text() 全量解析，避免大响应阻塞主线程（extension/content/inject.js）
  • P1-3 可靠性：彻底移除 checkStarredPublic 未认证 stargazers 兜底（60 次/小时 IP 限流 + Worker 共享出口 IP 的雷区），回查统一走 checkStarred 精确端点，无 token 且无缓存时降级而非误判（worker/src/github.js · worker/src/auth.js）
  • P1-4 可靠性：Snowflake 时间反推加运行时偏差自检——用权威 chat_sessions.created_at 与反推值持续对比，偏差超阈值自动禁用反推并降级到采集时刻，避免 TRAE 改 ID 策略时静默误归因（extension/content/inject.js）
  • P2-1 文档：README 第 137 行「加密存入 chrome.storage.local」虚假承诺已删除，改为如实说明「由当前系统用户 Profile 加密保护」；Key 真正加密存储属产品决策，待后续排期（README.md）
  • P2-3 文档：README「隐私优先 / 不上传」承诺已校正——明确默认本地优先、开启云端同步后会上传（含提问预览与来源 URL），区分"本地优先"与"可选云同步"（README.md）
结论整体评价

后端（worker）工程质量较高：CORS、OAuth、加密、超时重试均已按最佳实践落地，无明显 P0 风险。问题主要集中在扩展端性能热点与少量残留的安全/可靠性隐患。当前没有 P0 阻塞项，4 个 P1 建议在下一个版本排入。

一、安全 (Security) — 当前 6 个问题

P2安全 DeepSeek API Key 明文存储，且 README 虚假承诺「加密」（README 已修正）options.js:131 · popup.js:632

设置页 saveApiKey 直接 chrome.storage.local.set({ ttw_deepseek_key: key })，无任何加密；popup 用 Bearer ${key} 直连 DeepSeek。而 README 第 137 行写「（加密存入 chrome.storage.local）」——代码与文档不符。任何能访问浏览器 profile 的程序/扩展可读出该 Key。

修复建议
① 至少做 XOR+base64 混淆，或优先用 chrome.storage.session（内存级，关浏览器即失效）；② 修正 README，删除「加密」措辞，改为如实说明存储方式。
P2安全 Session token 仍在 URL query 中传递worker/src/auth.js:124-132

OAuth 完成后 Worker 302 到 /auth/done?token=xxx&expires=xxx。背景页通过 chrome.tabs.onUpdated 捕获后立刻关页，但 token 仍会：① 进入浏览器历史；② 被 Cloudflare 访问日志捕获——wrangler.toml 已开启 observability（10% 采样），日志含完整 request URL，token 有概率落入 Cloudflare 侧日志。

修复建议
改用 fragment（#token=xxx）或在 /auth/done 注入 content script 读 fragment 后 chrome.runtime.sendMessage；更稳妥是用 5 秒一次性 code 换 token（类 PKCE）。
P2安全/隐私 「隐私优先 / 不上传」承诺与云端同步行为存在张力（README 已修正）worker/schema.sql:47-69 · README L5/L36

README 首页与第四节反复强调「数据只存本地、不上传任何第三方、隐私优先」。但开启云同步时，usage_records 同步表会把 user_input_preview（用户提问预览）和 url 一并上传到服务器（extension/lib/sync.js:74 / worker/src/sync.js）。这与隐私卖点矛盾，且用户无明确告知「提问内容将离开本机」。

修复建议
① 同步开关旁明确列出将上传的字段（含提问预览），让用户知情同意；② 提供「同步时脱敏 user_input_preview」选项；③ 文案区分「本地优先（默认零上传）」与「可选云同步（会上传用量+提问预览）」。
P3安全 AES 密钥派生无盐、无迭代，且签名/加密同源worker/src/github.js:101-104

deriveAesKey 仍直接 SHA-256(SESSION_SECRET) 作 AES-GCM key。已用 AES-GCM + 随机 IV（良好），但缺盐、缺迭代、且 session 签名与 token 加密都源自同一 secret，无密钥分离。暴力破解成本偏低。

修复建议
改用 HKDF-SHA256，用不同 info 参数分别派生「session 签名密钥」与「token 加密密钥」。
P3安全 postMessage 使用通配符 * 作为 targetOrigininject.js:104 · content.js:38

主世界 → 隔离世界 的 usage 消息用 postMessage(..., '*')。载荷虽不含密钥，但含完整用量习惯数据，可被同页任意脚本接收。

修复建议
改为 window.postMessage(payload, location.origin)。
P3安全 Cloud-IDE-JWT 持久化到页面 localStorageinject.js:974-1005

为重放批量拉取，saveBulkAuth 把 trae.cn 的 Cloud-IDE-JWT 存进 __ttw_bulk_auth__（trae.cn 域 localStorage）。同域任意脚本（含 XSS）可读。建议仅内存保存。

修复建议
JWT 仅保留在内存变量 latestAuthToken，不写 localStorage；或写入 chrome.storage.session。

二、性能 (Performance) — 当前 6 个问题

P1已修复性能 Popup 每 5s 全量加载 2000 条记录 + 多遍遍历（已修复）popup.js:1170 · db.js:186

setInterval(renderSummary, 5000) 每次都执行：getSummary() → getAllRecords(2000) 后做 4 遍聚合；getComparison() → getRecordsSince(now-61天)；predictUsage()（60s 缓存，已缓解）。renderChanged 只减少了 DOM 重建，但 IndexedDB 全量加载与聚合每 5s 仍照常执行。重度用户 2000 条 × 多次遍历，popup 打开期间持续占用主线程。

修复建议
① 用 timestamp 索引做范围查询替代全量 getAll；② 汇总结果缓存，仅在有新记录写入时失效（监听 chrome.storage.onChanged 或 background 主动消息）；③ 改为事件驱动刷新，而非固定 5s 轮询；④ getComparison 拆成 3 个独立 IDBKeyRange 查询。
P1已修复性能 fetch/XHR 拦截器对每个匹配响应 clone().text() 读全量响应体（已修复）inject.js:700 · 781

对每个命中 shouldIntercept() 的响应都 response.clone().text() 读完整 body，再 JSON.parse。会话列表、代码补全等大响应（可达数 MB）会：① 内存翻倍（clone + text）；② 主线程 parse 阻塞页面；③ SSE 响应会等完整 body。

修复建议
① 先读 Content-Length/content-type，超阈值（如 100KB）跳过 body 解析；② SSE 用 ReadableStream 逐块解析，不等完整 body；③ 用 response.json() 替代 text()+JSON.parse。
P2性能 getComparison 加载近 61 天全量记录db.js:533

仅为计算「今日 vs 昨日 / 本周 vs 上周 / 本月 vs 上月」就加载 61 天记录（可能数千条）。

修复建议
用 3 个独立 IDBKeyRange 范围查询分别取各周期，或用 cursor 边遍历边累加。
P2性能 debug 在非调试态仍执行 slice(0,2000)inject.js:703

pushDebug({ bodyPreview: text.slice(0, 2000) }) 的 slice 总是执行，即使 DEBUG=false（pushDebug 内部直接 return）。大响应体下 slice 仍有开销。

修复建议
调用前先 if (DEBUG) 判断，或改惰性求值。
P3性能 浮窗 mousemove 监听在 removeWidget 后未解绑content.js:351-371 / 374

document.addEventListener('mousemove', ...) 在 bindWidgetEvents 中注册一次，removeWidget() 未移除。关闭浮窗后，页面每次鼠标移动仍触发该回调（仅 early-return）。

修复建议
仅在 mousedown 时注册 mousemove，mouseup 后移除；或在 removeWidget 中移除所有监听。
P3性能 内存 Map 仅按 size 阈值清理，非定时inject.js:109 / 592

ctxCache（60s TTL）、seenRequests（3s 窗口）只在 size 超阈值时清理过期项；增长缓慢时过期项不被及时释放。

修复建议
用 setInterval 定时清理（每 30s）。

三、稳定性 (Stability) — 当前 5 个问题

P2稳定性 EventSource onmessage 拦截只存引用不注册，页面收不到消息inject.js:852-859

对 trae/LLM 域 EventSource，Object.defineProperty(es,'onmessage',{set:(fn)=>{_onmsg=fn}}) 仅保存引用，未把 fn 注册到 EventSource。若页面用 es.onmessage = fn 设置监听，该 fn 不会被调用——页面在拦截域上的 SSE 功能会静默失效。

修复建议
在 setter 内同时 origAdd('message', fn)（注意去重），或在拦截前先桥接原有 onmessage。
P2稳定性 MV3 Service Worker：syncTimer 用 setTimeout，SW 终止后丢失background.js:114-122

syncTimer = setTimeout(...) 为内存变量。SW 在 30s 无活动后被终止，debounce 同步不执行（虽有 10min chrome.alarms 兜底，但实时性差）。

修复建议
用 chrome.alarms.create('ttw-sync-debounce', { delayInMinutes: 0.5 }) 替代 setTimeout，SW 重启后仍有效。
P3稳定性 WebSocket 直接替换构造函数 + prototype 共享inject.js:870-902

window.WebSocket.prototype = OriginalWebSocket.prototype 使 instanceof 与 ws.constructor === WebSocket 不可靠，可能破坏依赖这些判断的页面逻辑。

修复建议
用 new Proxy(OriginalWebSocket, { construct(target, args){...} }) 包装，而非替换构造函数。
P3稳定性 IndexedDB v1→v2 迁移 cursor.update 无 onerrordb.js:36-47

迁移时 cursor.update(rec) 没有 onerror 处理，单条失败（如配额超限）会静默跳过，部分旧记录回填 clientId 失败。

修复建议
为 cursor.update 加 onsuccess/onerror，迁移结束输出失败计数告警。
P3稳定性 浮窗 refreshTimer 在 SPA 路由切换后无 MutationObserver 兜底content.js:135

work.trae.cn 为 SPA，若路由切换把 widget host 从 DOM 移除，refreshTimer 仍会每 15s 向已失效的 shadow DOM 写数据，产生无效查询。

修复建议
用 MutationObserver 监测 host 是否仍在 document，移除则清理 timer 与状态。

四、可靠性 (Reliability) — 当前 9 个问题

P1已修复可靠性 checkStarredPublic 用未认证 GitHub API 暴力翻 1000 stargazer，受 60 次/小时 IP 限流（已修复）worker/src/github.js:77-97

老用户（登录时尚未持久化 access_token）触发 Star 回查时，checkStarredPublic 用未认证 GitHub API 翻最多 10 页 × 100 = 1000 个 stargazer 逐页比对。未认证 GitHub API 限流为 60 次/小时/出口 IP，而 Cloudflare Worker 共享出口 IP——多用户触发即迅速耗尽限额，返回 403 被当作「未 Star」，导致已 Star 用户被误拒免费诊断。

修复建议
① 登录流程强制持久化 access_token（已做主路径），彻底移除/弱化公开兜底；② 若保留兜底，对结果加服务端缓存并限制频率；③ 限流命中时返回「稍后重试」而非「未 Star」。
P1已修复可靠性 Snowflake ID 时间反推是未契约的启发式假设（已修复）inject.js:448-456

假设 TRAE session_id 前 8 位十六进制 = 创建时间秒。这是逆向推测，非官方 API 契约。一旦 TRAE 改 ID 生成策略（UUID / 增机器位 / 改精度），假设会静默失效：命中区间检查的非法 ID 会被错误归到某天，污染「今日/趋势」统计。当前仅用作 chat_sessions 映射未命中时的兜底，但兜底路径覆盖大量场景。

修复建议
① 运行时校验：若连续 N 条 snowflake 时间与 chat_sessions.created_at 偏差 > 10s，自动禁用反推并告警；② 文档明确标注此为「非官方假设，可能失效」；③ 优先保证 chat_sessions 映射命中率。
P2可靠性 官方 Worker 不可达时无预检，登录直接跳 404extension/lib/auth.js:59-66

loginWithGitHub 直接打开 Worker URL，无 /health 预检。若官方 Worker 临时挂掉，用户看到 GitHub 授权页 404 / 跳转失败，无明确提示。

修复建议
打开 OAuth 页前先 fetch('/health') 探活，不可达则提示「后端暂时不可用，请稍后或切自部署」。
P2可靠性 云同步无冲突解决（INSERT OR IGNORE 静默丢弃后到者）worker/src/sync.js:32

多设备并发 push 同一 client_id 时以先到者为准，后到被忽略。因同一会话累计用量会被覆盖式更新，后到的「更新快照」可能被丢弃，与「最新」不一致（虽同 client_id 通常通过 last-write 大致收敛，但跨设备时钟/顺序不保证）。

修复建议
改用 INSERT OR REPLACE 并按 ts/updated_at 比较是否覆盖；或拉取端标记冲突让客户端选择。
P3可靠性 sync pull 游标上报 fire-and-forgetextension/lib/sync.js:138-145

fetch('/api/sync/cursor', ...).catch(()=>{}) 失败不回退本地游标。实际本地 lastPullServerTs 已先更新，影响小，但可能浪费带宽重复拉取。

修复建议
改为 await，或将服务端游标视为 best-effort，pull 时由本地 since 决定增量。
P3可靠性 客户端 addRecord 无严格字段校验db.js:80-131

本地 addRecord 仅套默认值，不 clamp 负数 token、不限制 url/model 长度。服务端 num()/flo() 已 clamp，但本地库可能存入负数/超长字段，影响统计与导出。

修复建议
入口做白名单 + 类型/范围校验：Math.max(0, Math.floor(n)) 对 token；String(v).slice(0,2000) 对字符串。
P3可靠性 导出无校验和 / 原子范围options.js:306-346

CSV/JSON 导出不含记录数校验和；导出过程中若有新记录写入，预览数与文件数可能不一致。

修复建议
导出时锁定范围、文件头含记录数与 checksum；导入时校验。
P3可靠性 Worker 错误响应无统一错误码worker/src/index.js:80

所有错误统一返回 {error: message}，客户端只能按 HTTP status 分支，无法程序化区分业务错误（如 NOT_STARRED / QUOTA_EXCEEDED）。

修复建议
统一为 {error: message, code: "..."}，扩展端据此精确提示。
P3可靠性 OAuth 登出后端删除 session 为 fire-and-forgetextension/lib/auth.js:74-77

logout() 先本地清 session，再 best-effort 通知后端删除；若请求失败，后端 session 残留至 7 天 TTL。本地已清，风险低。

修复建议
await 后端删除，失败提示用户「本地已登出，服务端 session 将在过期后失效」。
