## 浮窗最小化后无法拖动（content.js）
- 根因：拖拽 `mousedown` 只绑定在 `header` 上；浮窗收起(collapsed)时 CSS 把 `header` 设为 `display:none`，只剩 `collapsed-body` 可见且无拖拽监听，导致收起后整条无法拖动。
- 修复（`extension/content/content.js`）：

- 注意：content script 改动需在 `chrome://extensions` 重新加载扩展才生效。

## 会话明细：滚动到底自动加载更多，最多一个月
- 位置：`extension/popup/popup.js` 的 `renderSessions`（会话级明细列表，原本 `slice(0,30)` 一次性渲染，无滚动加载、无时间限制）。

## 修复后引入的回归（用户反馈「数据都没了」）
- 根因：`db.js` `getSummary` 把 `const records = await getRecordsSince(now - SUMMARY_WINDOW_DAYS * dayMs)` 写在 `const now`/`const dayMs` 声明**之前**。`const` 有暂时性死区（TDZ），运行时在 192 行引用未初始化的 `now` 抛 `ReferenceError: Cannot access 'now' before initialization` → `getSummary()` 崩溃 → popup 整页空（IndexedDB 数据未丢，只是读不出）。
- 坑：`node --check` 只查语法不查 TDZ，所以上一轮「6 文件全过」漏掉了这个运行时错误。
- 修复：把 `const now = Date.now(); const dayMs = 24*60*60*1000;` 移到 `getRecordsSince(...)` 之前（db.js:190-194）。重新 `node --check` 6 文件全 OK。
- 教训：改动涉及「把原本不引用某变量的行，换成引用该变量的行」时，必须确认被引用变量已在作用域内先声明；`node --check` 不足以证明运行时正确，需人工读作用域或跑单测。
- 注：修复后 summary 范围仍为近 30 天（SUMMARY_WINDOW_DAYS），超 30 天的数据不进汇总/会话明细视图，但仍在 IndexedDB 中（属预期性能取舍，非丢失）。
- 用户侧：需在 `chrome://extensions` 重新加载扩展才会生效。

## Bug：清空本地数据后无法获取数据（水位线依赖易失游标）
- 根因：`sync.js` `pull()` 用持久化游标 `state.lastPullServerTs`（存 `chrome.storage.local` 的 `ttw_sync_state`）做增量拉取水位线。清空 IndexedDB 时该游标**不被清**（尤其 DevTools 清空），导致拉取从旧时间戳开始、服务端 `server_created_at > since` 无新数据返回 → 卡死「无法获取数据」。设计上本不该用独立存储的「上一次获取数据时间」。
- 用户要求：水位线应取「历史数据最新那条的时间」。
- 前置缺口：原 `importRecords` 注释明说「server_created_at 字段会被忽略」，本地记录无服务端时间戳，无法直接取。
- 修复：
  1. `db.js` `importRecords` 现存储 `serverCreatedAt: r.server_created_at || 0`。
  2. `db.js` 升 `DB_VERSION` 3→4，`onupgradeneeded` 补 `serverCreatedAt` 索引（store 创建分支 + 新增 `e.oldVersion < 4` 迁移分支，带 indexNames 守卫）。
  3. `db.js` 新增 `getMaxServerCreatedAt()`：按索引 `openCursor(null,'prev')` 取最大；索引缺失/无记录返回 0（→ 全量拉取）。
  4. `sync.js` `pull()`：`let since = await getMaxServerCreatedAt()` 取代 `state.lastPullServerTs`；移除 pull 内未用的 `getSyncState` 调用。仍 `setSyncState({lastPullServerTs})` 仅作服务端游标上报。
- 验证：worker `/api/sync/pull` SELECT 含 `server_created_at`，`rowToClient` 映射到响应记录；db.js / sync.js `node --check` 通过。in-app「清空本地数据」按钮仍调 `resetLocalCursor`（顺带重置 push 游标 lastSyncedLocalId），保留作防御。
- 已知小瑕疵：本地「已捕获但未回拉」的记录无 serverCreatedAt，增量拉取会每次重新 fetch 该记录（clientId 去重跳过，无重复、仅微小带宽浪费）。根治需在 push 时回写 serverCreatedAt（worker push 响应当前只回计数）。

## 清空后「完全拿不到数据」的真正根因（用户复现「还是不行」）
- 关键认知：上一轮修的 `getMaxServerCreatedAt` 水位线是对的，但即使 pull 把全量历史拉回 IndexedDB，popup 仍显示空——因为 `getSummary` 取数窗口 `getRecordsSince(now - 31天)` 把 >31 天的记录挡在视图外，`all`/`bySession`/`byModel` 都只聚合 31 天窗口内数据；且 `popup.js` 会话明细再用 `oneMonthAgo` 过滤只显示近 31 天。用户 TRAE 历史大多 >31 天，清空后从云端恢复的历史被双重窗口过滤 → 「数据都没了」的体感。
- 这是上一轮 P1-1「性能优化」引入的回归：原 `getAllRecords(2000)` 是**全量**（最多 2000 截断），改 31 天窗口后老历史不再进汇总/明细视图。
- 修复：
  1. `db.js` `getSummary` 取数由 `getRecordsSince(now - 31d)` 改为 `getRecordsSince(0)`（索引范围下限 0=全表，不被 2000 截断，仍走索引查询）；`all`/`bySession`/`byModel` 现为真实全量；趋势图展示仍 `slice(-14)`，月桶用 `startOfMonth`。性能由事件驱动刷新(ttw_usage_ping)+并发守卫+15s 兜底保证。
  2. `popup.js` `renderSessions` 去掉 `oneMonthAgo` 硬过滤（`const nextData = bySession;`），明细展示全部会话（列表已分页 SESSION_PAGE=30，全量无性能问题）；hint 文案由「近一个月 N 个」改为「共 N 个会话」。
  3. `options.js` `clearLocalData` 清空后立刻 `await getStatus().canSync ? pull() : 跳过`，主动从云端恢复历史，消除「清空后自动同步未被触发」这一潜在因素。
- 校验：db.js / popup.js / options.js `node --check` 通过。
- 结论：清空后「完全拿不到」= pull 水位线(已修) + 取数/明细双重 31 天窗口(本次修) 叠加。三处修完，清空后重载扩展 → 历史数据即可见。

## Bug：清空后 bulk 主动拉取只查 140 秒窗口、返回空（用户贴出实际请求）
- 现象：用户确认请求能发起，但 `start_time/end_time` 窗口仅 140 秒（如 1786568550~1786568690），返回空。这是增量拉取 `sinceSec = BULK_LAST_END_KEY` 路径。

- 用户原则（命中要害）：「不该用上一次获取时间，该用历史最新一条的时间」。
- 修复（彻底用真实数据库水位线，清空即归零）：
  1. `db.js` 新增 `getMaxUsageTime()`：取 `timestamp` 索引倒序第一条（max），无记录/索引缺失返回 0。
  2. `background.js` import `getMaxUsageTime`；消息路由新增 `case 'TTW_GET_MAX_USAGE_TIME'` → `getMaxUsageTime().then(v=>sendResponse({value}))`（return true 异步响应）。
